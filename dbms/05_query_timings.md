# Query Benchmark Results

## 1. Introduction

The purpose of this document is to evaluate the performance of selected SQL queries used in the Forma application.

The benchmarking was performed using PostgreSQL's `EXPLAIN (ANALYZE, BUFFERS)` command to analyze query execution time, scan methods, index usage, and execution plans.

Five representative READ queries were selected from the existing `04_queries.sql` file. Each query was executed three times, and the average execution time was calculated.

The benchmarking was conducted on the `forma_benchmark` database containing synthetic test data.

## 2. Benchmarking Methodology

The following methodology was used:

1. Five representative READ queries were selected from `04_queries.sql`.
2. Each query was executed three times using `EXPLAIN (ANALYZE, BUFFERS)`.
3. Execution times were recorded in milliseconds.
4. The average execution time was calculated for each query.
5. Execution plans were saved separately in the `dbms/plans/` directory.

### 2.1 Selected Queries

| Query ID | Description | Operation |
|---|---|---|
| R1 | Find user by email | SELECT with filtering |
| R3 | Find pending invitations | SELECT with filtering |
| R4 | Workspaces with board count | JOIN, aggregation and sorting |
| R5 | Get workspace details | SELECT with filtering |
| R6 | Get boards in a workspace | SELECT with filtering and sorting |

## 3. Query Execution Timings

All execution times are measured in **milliseconds (ms)**.

The average execution time is calculated using the three recorded executions of each query.

| Query ID | Query Description | Run 1 (ms) | Run 2 (ms) | Run 3 (ms) | Average (ms) |
|:---:|---|---:|---:|---:|---:|
| R1 | Find user by email | 0.085 | 0.092 | 0.117 | **0.098** |
| R3 | Find pending invitations | 0.070 | 0.095 | 0.068 | **0.078** |
| R4 | Workspaces with board count | 0.322 | 0.234 | 0.633 | **0.396** |
| R5 | Get workspace details | 0.071 | 0.053 | 0.055 | **0.060** |
| R6 | Get boards in a workspace | 0.468 | 0.176 | 0.241 | **0.295** |

## 4. Execution Plan Analysis

The execution plans generated by PostgreSQL were analyzed to understand how each query accesses and retrieves data.

### 4.1 R1 – Find User by Email

- **Scan Type:** Index Scan
- **Index Used:** `User_email_key`
- **Rows Returned:** 1

PostgreSQL uses the unique index on the email column to locate the requested user efficiently.

### 4.2 R3 – Find Pending Invitations

- **Scan Type:** Index Scan
- **Index Used:** `BoardInvitation_email_idx`
- **Additional Filter:** `status = PENDING`
- **Rows Returned:** 1

PostgreSQL uses the email index to find matching invitations and then applies the status filter to retrieve pending invitations.

### 4.3 R4 – Workspaces with Board Count

- **Join Operation:** Nested Loop Left Join
- **Aggregation:** GroupAggregate
- **Scan Types:** Bitmap Heap Scan and Bitmap Index Scan
- **Indexes Used:** `Workspace_ownerId_idx`, `Board_workspaceId_idx`
- **Rows Returned:** 2

This query retrieves workspaces owned by a particular user and calculates the number of boards in each workspace. It uses joins, aggregation, and sorting operations.

### 4.4 R5 – Get Workspace Details

- **Scan Type:** Index Scan
- **Index Used:** `Workspace_pkey`
- **Additional Filter:** `ownerId`
- **Rows Returned:** 1

PostgreSQL uses the primary-key index to locate the workspace and then checks whether the workspace belongs to the specified owner.

### 4.5 R6 – Get Boards in a Workspace

- **Join Operation:** Nested Loop
- **Scan Types:** Bitmap Heap Scan, Bitmap Index Scan and Index Scan
- **Indexes Used:** `Board_workspaceId_idx`, `Board_ownerId_idx`, `Workspace_pkey`
- **Sorting Method:** Quicksort
- **Rows Returned:** 5

PostgreSQL uses the workspace ID and owner ID indexes together to retrieve matching boards. It then uses the primary-key index to verify workspace ownership and sorts the results by `updatedAt` in descending order.

## 5. Performance Observations

Based on the execution timings and execution plans, the following observations were made:

1. **Index Usage:** Queries R1, R3, and R5 use index scans to retrieve records based on indexed columns.
2. **Filtering:** R3 uses the email index and applies an additional filter on the invitation status.
3. **Joins and Aggregation:** R4 involves a Nested Loop Left Join and GroupAggregate operation, making its execution plan more complex.
4. **Sorting:** R4 and R6 involve sorting operations to arrange the retrieved records.
5. **Execution Time:** Among the selected queries, R5 has the lowest recorded average execution time of 0.060 ms, while R4 has the highest average execution time of 0.396 ms.

## 7. Conclusion

The performance benchmarking of five representative READ queries was completed using PostgreSQL.

Each query was executed three times, and the average execution time was calculated to provide a more consistent performance measurement.

The execution plans helped identify the indexes, scan methods, joins, aggregation, and sorting operations used by PostgreSQL.

The results demonstrate how the existing database indexes support data retrieval and how query complexity influences execution time.

The benchmark provides a baseline for evaluating and improving the performance of the Forma database.
